## 更正：伤害公式的三处过时描述（重新读代码后）

昨天（09-11）记的「战斗伤害模拟器网页」里的关键数值有**三处已经和当前代码不符**，
代码改过而记忆没跟上。以本条为准：

1. **普攻不再吃兵科伤害倍率**。`combat.ts:69` 注释写得很明确：
   「科技『训练/专精』只加成战法威力，普攻不再吃兵科伤害倍率」。
   科技对普攻的影响只剩两项，且都是**加减不是乘**：
   - `troopAttackTechBonus`（武器精造 / 装甲）：枪戟弩骑 +10 攻击，**折算进武力**
   - `troopDefenseTechBonus`（防具精造 / 装甲）：+10 防御，**折算进统率**（影响统率差乘区）

2. **普攻暴击不是概率，是特技决定**。`normalAttackIsCritical`（`skills/rules/combat.ts:11`）

   = `clamp(5 + max(0, 武力−60)×0.35 + (S:+8 / A:+4), 5, 30)`（`officerAbilities.ts:97`）。
3. **战法兵科科技是 +0.1 / 再 +0.25**，不是 +0.1 / +0.1。见 `techs.ts:246 tacticPowerMultiplier`：
   1 级节点 +0.1，4 级节点 +0.25，合计 1.35。

另外补两个此前遗漏的乘区：

- **远程衰减**（`combat.ts:74-77`）：距离 ≥2 时 `max(0.5, 1 − (距离−1) × 每格衰减)`，

## 发现：残兵衰减后 MIN_ATTACK_DAMAGE(120) 已基本成为死参数

给 clamp 做解释时顺手算的边界，结论供调数值时参考：

- 地板 `round(120 × α)` 现在**几乎不可能触发**。取统率 80 / 武力 75 时 `raw ≈ 0.385 × committed`，
  地板是 `0.12 × committed`，raw 恒为地板的 3.2 倍。再叠最恶劣乘区
  （统率差 0.8 × 丘陵 0.8 × 随机 0.92 × 守方光环 0.95 × 反击 0.6 ≈ 0.34）仍高于地板。
  满编时 `raw ≈ 563~893`，也远超 120。
- 上限 `2200` 对**单次普攻也不触发**：满编极限约 `893 × 1.74 ≈ 1554`。
  它实际只在**战法**（再 × 威力 × 适性 1.2 × 兵科 1.35 × 暴击 1.35）和**齐攻**（多队求和）时起作用。
- 换句话说：加了 `commitmentScale` 之后，120 这个地板从「保底伤害」退化成了纯安全网。
  若以后想给残兵一个真实下限，得单独设一个不随 α 缩放的常数，而不是复用 `MIN_ATTACK_DAMAGE`。

## 约定：给用户写公式时 clamp 统一用 (值, 下限, 上限)

踩过一次坑：给用户**讲定义**时用 `clamp(值, 下限, 上限)`，转头**写公式**时照抄代码里
`Math.min(上限, Math.max(下限, 值))` 的嵌套顺序，写成了 `clamp(0.8, 1.2, 值)`，
用户当场发现「值是早就知道的 0.8、下限 1.2」读不通。

- 根因：JS 无内置 clamp，代码里是 `Math.min(hi, Math.max(lo, x))` 嵌套，**从外向内读是 上限→下限→值**，
  与「值在前」的数学记号顺序相反。（反过来嵌 `Math.max(lo, Math.min(hi, x))` 结果等价。）
- 约定：对外写公式一律 `clamp(值, 下限, 上限)`，并**同时附上代码原文**，避免再对不上。
- `docs/GAME_RULES.md` 里的写法本来就是对的，只有聊天里的公式写错了，不要误改文档。
- 待办（用户未答复）：可考虑在 `src/game/battle/` 加 `clamp(value, min, max)` 工具函数，
  替换散落的 `Math.min(hi, Math.max(lo, x))`。

## 洞察：240 基数项到底在干什么（用户问「直接 α × committed 不行吗」）

用户的质疑是对的：**1000 兵以下，`240 × α` 退化成了 `0.24 × committed`，只是个系数，没有独立作用。**

- 因为 `α = committed/1000`，展开得 `240 × α = 0.24 × committed`。
- 残兵区间整条公式可合并为 `raw = committed × (0.32 + 统率/2000 + 武力/3000)`，
  与「去掉 240」的 `committed × (0.08 + ...)` **形状完全相同**，都是过原点直线，只是斜率 0.385 vs 0.145。
- **240 的真正作用只在 `committed >= 1000`**：此时 `α ≡ 1`，240 是常数项，把曲线整体抬高，
  使伤害对兵力**次线性**。实测（统率80/武力75，k=0.145）：
  | 兵力 | 有240 | 无240 | 伤害倍数（有/无） |
  |---|---|---|---|
  | 1000 | 385 | 145 | — |
  | 2000 | 530 | 290 | 1.38 / 2.00 |
  | 4000 | 820 | 580 | 2.13 / 4.00 |
  即：有 240 时 4 倍兵力只换 2.13 倍伤害；去掉则完全线性。
- 240 的第二个作用：**压缩能力差距**。4000 兵下强将(统80武75) vs 弱将(统1武1)：
  有 240 → 820 : 563 = 1.46 倍；无 240 → 580 : 323 = 1.80 倍。
- 结论：`240 × α` 让 240 有**两种身份**——满编时是常数项（制造次线性），残兵时是线性项（并入斜率）。
- 文档建议（用户未答复）：`GAME_RULES.md` 第 10 节可补**分段写法**，比单行 `240 × commitmentScale + attackScore` 直观：
  ```text
  committed >= 1000:  raw = 240 + committed × k
  committed <  1000:  raw = committed × (0.24 + k)
  ```
  两段在 `committed = 1000` 处正好接上（同为 `240 + 1000k`），连续无跳变。

## 核实：兵种适性只影响战法，完全不影响普攻

用户问「有考虑武将的兵种适性吗」。全量搜索 `aptitude` 后结论：

- **战法路径用适性，共三处**（`officerAbilities.ts` / `catalog.ts` / `legacyCore.ts`）：
  1. 解锁门槛：`TACTIC_REQUIRED_APTITUDE = { 1:'B', 2:'A', 3:'S' }`，即 S 可用 1/2/3 级、A 可用 1/2 级、
     B 仅 1 级、**C 完全不能用战法**（`maxTacticTier` 返回 0）。
  2. 伤害倍率：`TACTIC_APTITUDE_DAMAGE = { C:1, B:1, A:1.1, S:1.2 }`。
  3. 暴击率加成：`tacticCriticalChance` 里 S +8、A +4、B/C +0（再整体 clamp 到 5~30）。
  实际效果：战法伤害 = power × 适性倍率，而高级战法本身 power 更高（枪 1.18/1.23/1.27，骑 1.4/1.45/1.5），
  所以 **S 比 B 的战法伤害高约 1.29 倍**（1.076 × 1.2）。
- **普攻 / 反击 / 一齐攻击完全不读适性** —— `computeNormalAttackDamage` / `damageRoll` / `damageForRoll`
  都没有 aptitude 参数。这是有意设计：适性 = 战法专精程度。
- 取值规则（`effectiveUnitAbilities`）：**统率取主将**（`leader.stats.leadership`），
  **武力、智力、适性都取编队中最高者**（`firstMaximum`）。所以**副将能补武力/智力/适性，但补不了统率**。
- 特例：`aptitudeKey` 对 **运输队和剑兵（sword）返回 null**，即这两类部队没有适性，永远不享受加成、也不能用战法。
- 移动力、移动规则不使用适性。`DeployDialog` 里适性仅用于武将列表排序与展示，不限制选择。

## 追加 2：页脚吸底 + 重新标定 dvh 常数（这次是真踩了坑）

上一轮的 `calc(100dvh - 356px)` **常数标错了**：356 是按「页脚没有内边距」量的，
这一轮给页脚加了 `padding: 10px 14px` 做吸底，开销涨到 **334px**（重测值），
于是矮屏下 `.tech-tree-panel` 自己冒出了滚动条
（1366×768：SVG 412 装进 400 的容器；1024×600：244 装进 232）。
844×390 更惨——`390-356=34`，科技树被压成 **34px 的细条**，完全不可读。

最终写法：
```css
.tech-tree-svg { max-height: clamp(220px, calc(100dvh - 375px), 560px); }
```
- `375` = 实测开销 334 + 约 40px 余量；
- **下限 220px 不能省**：没有下限时极矮视口会把树压成细条，不如让它保持可读尺寸、
  和弹窗一起滚动。下限也不能设太高——必须在 1024×600（可用 227px）以内，
  否则小窗口笔记本就会白多出滚动条。220 是这两个约束夹出来的值；
- 页脚吸底：`position: sticky; bottom: 0; z-index: 2; margin: 16px -14px 0; padding: 10px 14px;
  background: var(--panel); backdrop-filter: blur(6px);`
  （左右负外边距 + 内边距是为了让底色铺满弹窗内边距，滚动内容不从两侧透出；
  `backdrop-filter` 用来盖住 `--panel` 那 7% 的透明）。

最终实测（6 档）：

| 视口 | 弹窗 | 弹窗滚动 | 树面板滚动 | 树高 | 确认键 |
|---|---|---|---|---|---|
| 1920×1080 | 780×859 | 无 | 无 | 521 | 可见 |
| 1440×900 | 780×859 | 无 | 无 | 521 | 可见 |
| 1366×768 | 780×731 | 无 | 无 | 393 | 可见 |
| 1024×600 | 780×563 | 无 | 无 | 225 | 可见 |
| 844×390（手机横屏） | 780×358 | 有 | 有 | 220 | **可见**（吸底兜住） |
| 720×450 | 672×418 | 无 | 有 | 220 | 可见 |

**已知限制**：844×390 是手机横屏，宽度 >700 不触发移动端布局，
走桌面布局后科技树只有 0.42 倍缩放，字不可读。这是响应式断点的问题，
不是这次改动引入的，真要修得给横屏单独做断点。
