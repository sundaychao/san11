# 武将特技系统设计

状态：已通过对话确认，等待书面复核
日期：2026-08-18

## 1. 目标

建立可持续扩展的武将特技框架，在不让移动、战斗、计略、设施、回合和内政模块堆积大量特技名称判断的前提下，逐批实现《三国志11》原版一百种特技，并继续支持项目已有的自定义特技。

第一阶段先完成完整框架和十五个代表性特技，覆盖移动、普通攻击、战法、计略、设施、部队回合、城市命令及城市收入。后续特技沿用相同接口分批增加。

## 2. 已确认规则

- 每名武将保留一项特技，继续使用现有 `Officer.skill?: string` 存档字段。
- 部队主将和所有副将的特技都生效。
- 同一部队或同一城市内的同名特技只生效一次，但保留全部来源武将供界面和战报查询。
- 不同特技是否叠加由效果类型统一规定，不允许业务代码自行决定结算顺序。
- 武将已行动不影响被动特技。
- 正在所属城市执行兵装生产任务的武将仍视为驻城；调动途中、已编入部队和在野武将不视为驻城。
- 单机和联网调用同一套纯规则函数，所有随机效果继续使用 `seed`、`rngCursor` 和 `nextRandom`。
- 第一阶段分批实现，不一次写完全部一百种效果。

## 3. 双重分类

### 3.1 展示分类

界面和资料查询保留原版分类：

- 行军 9：飞将、遁走、强行、长驱、推进、操舵、踏破、运搬、解毒。
- 攻击 35：扫讨、威风、昂扬、连战、急袭、强袭、乱战、攻城、掎角、捕缚、精妙、强夺、心攻、驱逐、射程、白马、辅佐、枪将、戟将、弓将、骑将、水将、勇将、神将、斗神、枪神、戟神、弓神、骑神、工神、水神、霸王、疾走、射手、猛者。
- 防御 8：不屈、金刚、铁壁、怒发、藤甲、强运、血路、护卫。
- 计略 20：待伏、火攻、言毒、机智、诡计、虚实、妙计、秘计、看破、洞察、火神、神算、百出、鬼谋、连环、深谋、反计、倾国、妖术、鬼门。
- 辅助 7：规律、沉着、明镜、乐奏、诗想、筑城、屯田。
- 内政 8：名声、能吏、繁殖、发明、造船、指导、眼力、论客。
- 收入 4：富豪、米道、征税、征收。
- 灾害 8：亲乌、亲羌、亲越、亲蛮、威压、仁政、风水、祈祷。
- 关系 1：内助。

### 3.2 实现分类

实现不依赖展示分类，而按触发机制分为：

1. 规则修正：移动力、ZOC、范围、消耗、成功率、暴击和伤害倍率。
2. 行动反应：攻击、受击、计略成功、部队击破后产生的额外效果。
3. 回合结算：本势力回合开始、旬补给和状态结算时触发。
4. 城市命令：只修正执行征兵、生产、搜索等命令的武将。
5. 城市被动：根据驻城武将修正月度、季度收入或城市事件。
6. 独立系统：俘虏、技巧、外交、忠诚、婚姻和异民族等尚未具备完整模型的系统。

展示分类只用于名称、筛选和说明；一个特技可以包含多个不同实现分类的效果。例如飞将同时提供移动 ZOC 豁免和战法暴击，火神同时影响计略成功、火焰伤害和火计防御。

## 4. 目录与职责

```text
src/game/skills/
  types.ts                  特技 ID、分类、效果、上下文和结果类型
  registry.ts               合并原版与自定义特技，按名称查询定义
  sources.ts                解析部队、城市和命令的生效特技与来源
  stacking.ts               去重、叠加、优先级和统一取整规则
  index.ts                  稳定的公开导出入口
  catalog/
    movement.ts             原版行军特技定义
    attack.ts               原版攻击特技定义
    defense.ts              原版防御特技定义
    strategy.ts             原版计略特技定义
    support.ts              原版辅助特技定义
    domestic.ts             原版内政特技定义
    income.ts               原版收入特技定义
    disaster.ts             原版灾害特技定义
    relationship.ts         原版关系特技定义
    custom.ts               项目自定义特技定义
  rules/
    movement.ts             移动、地形和 ZOC 规则投影
    combat.ts               普攻、战法、暴击、伤害和防御规则投影
    strategy.ts             计略范围、消耗、成功、免疫规则投影
    facility.ts             建设与修补规则投影
    city.ts                 城市命令、收入和城市事件规则投影
    turn.ts                 部队及势力回合开始规则投影
  handlers/
    chainStrategy.ts        连环等多目标计略后续效果
    index.ts                复杂处理器白名单和穷尽分派
```

`catalog` 负责声明“特技有什么效果”，`sources` 负责声明“当前有哪些特技”，`rules` 负责声明“这些效果怎样修改某一领域规则”，`handlers` 只承载不能用普通规则修正表达的复杂状态变化。

现有 `src/game/battle/actions.ts` 继续作为兼容导出入口。第一阶段只让现有领域模块调用特技公开接口，不改变组件、联网 intent 或 Socket.IO 事件名称。

## 5. 类型模型

### 5.1 定义和状态

```ts
type SkillImplementationStatus = 'active' | 'planned' | 'blocked';

interface SkillDefinition {
  name: string;
  displayCategory: SkillDisplayCategory;
  description: string;
  implementationStatus: SkillImplementationStatus;
  effects: SkillEffect[];
  blockedBy?: SkillSystemDependency[];
}
```

- `active` 表示效果已接入并有自动化测试。
- `planned` 表示已进入一百种原版目录，但尚未实现效果。
- `blocked` 表示依赖当前不存在的俘虏、技巧、外交、忠诚、婚姻或异民族系统。
- 未登记字符串仍可作为自定义特技显示和排序，但不会参与结算，也不会导致读取旧存档失败。

### 5.2 效果采用判别联合

```ts
type SkillEffect =
  | { kind: 'movementAllowance'; add: number; troopTypes?: TroopType[] }
  | { kind: 'ignoreEnemyZoc'; terrain: 'land' | 'water' }
  | { kind: 'tacticCritical'; mode: 'guaranteed'; condition: SkillCondition; troopTypes?: TroopType[] }
  | { kind: 'normalAttackCritical'; mode: 'guaranteed'; condition: SkillCondition }
  | { kind: 'repeatNormalAttack'; chance: number }
  | { kind: 'negateIncomingDamage'; chance: number; condition: SkillCondition }
  | { kind: 'strategyEnergyCost'; set: number }
  | { kind: 'strategyGuaranteed'; strategyIds: StrategyId[]; condition: SkillCondition }
  | { kind: 'strategyImmunity'; strategyIds: StrategyId[] | 'all' }
  | { kind: 'fireDamageMultiplier'; multiplier: number }
  | { kind: 'buildPowerMultiplier'; multiplier: number }
  | { kind: 'turnStartEnergy'; add: number }
  | { kind: 'commandYieldMultiplier'; command: GameCommand['type']; multiplier: number; armamentTypes?: ArmamentType[] }
  | { kind: 'cityIncomeMultiplier'; resource: 'gold' | 'food'; multiplier: number }
  | { kind: 'complexHandler'; handler: ComplexSkillHandlerId };
```

每一种效果都有明确字段和处理模块。增加非法字段或遗漏处理分支时，TypeScript 和穷尽测试必须失败。条件同样使用判别联合，例如 `targetWarLower`、`targetIntelligenceLower`、`troopsBelow`，不接受任意字符串表达式或运行时脚本。

## 6. 生效来源解析

### 6.1 部队

```ts
resolveUnitSkills(state: GameState, unit: ArmyUnit): ActiveSkill[]
```

按主将、第一副将、第二副将顺序读取武将。结果按特技名称去重，并在 `sources` 中保留所有提供该特技的武将 ID。属性来源和特技来源互相独立：最高武力武将可以提供战法属性，另一名副将可以提供神将效果。

### 6.2 城市

```ts
resolveCitySkills(state: GameState, cityId: CityId): ActiveSkill[]
```

只有 `forceId` 与当前城市拥有者一致，并且 `location` 为该城 `city` 或该城 `task` 的武将参与。`unit`、`transfer`、`unaffiliated` 不参与。城市同名特技去重。

### 6.3 命令

```ts
resolveCommandSkills(state: GameState, command: GameCommand): ActiveSkill[]
```

只返回执行该命令的武将特技。名声、能吏等命令特技不会因为同城其他武将拥有而生效。

## 7. 规则投影与复杂处理器

领域模块先计算基础规则，再将基础规则和上下文传入特技规则投影函数：

```ts
const rules = resolveTacticSkillRules({ state, attacker, target, tactic }, baseRules);
```

规则投影函数不修改 `GameState`，只返回完整规则值。调用方仍负责验证、随机、扣费、伤害和报告。

复杂处理器只允许从 `ComplexSkillHandlerId` 白名单调用。处理器接收窄化后的事件上下文并返回新的状态或明确的补丁，不读取 React、DOM、音频、Socket.IO 或模块级可变状态。第一阶段只有连环需要复杂处理器。

## 8. 叠加和优先级

每类效果在 `stacking.ts` 中固定策略：

- 同名特技：`unique`，只结算一次。
- 布尔豁免和必定效果：`booleanOr`，任一满足即成立。
- 同类固定值：`highest`，例如多个“消耗设为固定值”取最有利值。
- 明确可累计的加值：`add`，先相加后应用。
- 倍率：默认 `highest`；只有效果类型明确声明 `multiply` 时才连乘。
- 互斥覆盖：按效果类型定义的固定优先级，不按武将数组或对象遍历顺序决定。

数值统一执行“基础值、加值、倍率、一次取整、上下限”。随机判定按固定行动流程消耗随机游标，未触发对应随机阶段时不得提前消耗随机数。

## 9. 固定行动结算顺序

所有涉及特技的行动遵循：

1. 解析特技来源。
2. 计算合法性、范围和目标规则。
3. 计算行动力、气力、资金和其他消耗。
4. 计算命中、成功、暴击及伤害免除判定。
5. 计算基础伤害、攻击修正和防御修正。
6. 原子修改部队、设施、城池和资源状态。
7. 执行连战、连环、吸兵、反计等后续反应。
8. 生成现有伤害报告、计略报告和游戏日志。

验证失败不扣资源、不消耗随机游标，也不触发特技后续反应。

## 10. 城市与时间结算

富豪和米道只修改该次基础收入，不修改城市已有资源，也不修改随机事件、战利品、运输和命令支出。

- 富豪：现有月度金收入乘 `1.5`。
- 米道：现有季度粮食收入乘 `1.5`。
- 富豪与米道可以同时生效。
- 多名同名特技武将驻城不重复叠加。

部队回合特技只在所属势力开始操作前触发。乐奏只恢复当前开始行动势力的相应部队，不在对方势力开始行动时重复恢复。该规则沿用现有单机和联网的分势力回合入口。

## 12. 暂未实现特技

原版一百种特技全部进入目录，但第一阶段之外标记为 `planned` 或 `blocked`。下列依赖未建立前不伪造效果：

- 水军战法和完整水上障碍：推进、操舵、水将、水神等只能在对应玩法具备后激活完整效果。
- 俘虏、战死、负伤和宝物：捕缚、强夺、猛者、强运、血路、护卫。
- 技巧点和技巧研究：精妙、指导。
- 外交和舌战：论客。
- 忠诚：仁政。
- 婚姻：内助。
- 异民族据点：亲乌、亲羌、亲越、亲蛮、威压。

已有同名或自定义字符串继续显示。自定义特技只有加入 `catalog/custom.ts` 并通过测试后才成为 `active`。

## 13. UI 与存档兼容

- `Officer.skill?: string` 保持不变，不提升 `schemaVersion`。
- 武将列表、出征选择和详情界面继续显示原字符串。
- 注册表提供名称、分类、说明和实现状态供后续详情 UI 使用，但第一阶段不重新设计界面。
- 旧存档中的未知特技不报错、不丢失。
- `ActiveSkill` 和规则投影结果全部为派生数据，不写入 SQLite 或本地存档。
- 联网 intent 和房间快照结构不增加特技动作字段；特技由服务器和客户端从相同状态确定性推导。

## 14. 错误处理

- 注册表启动测试必须检查原版目录恰好一百个名称且无重复。
- `active` 特技不得缺少效果；`blocked` 特技必须声明依赖系统。
- 未知特技按仅展示处理，不抛出运行时异常。
- 复杂处理器 ID 未注册时在开发和测试环境抛出明确错误。
- 特技不能绕过原有行动归属、目标存在、资源充足和部队行动状态校验，除非其效果类型明确修改该项合法性。
- 所有状态修改继续使用现有原子式克隆流程；失败时原状态不变。

## 15. 测试与验收

### 15.1 单元测试

- 目录包含一百种原版特技，名称无重复，展示分类数量为 9、35、8、20、7、8、4、8、1。
- 未知特技可显示但不产生效果。
- 主将和副将特技共同生效，同名特技去重并保留来源。
- 驻城、任务中、出征、调动和在野武将的城市特技判定正确。
- 每种效果类型的叠加、取整、优先级和条件判断正确。
- 第一阶段十五个特技各有成功、失败和不满足条件测试。
- 随机特技在同一种子和游标下结果一致，且只消耗规定数量的随机值。

### 15.2 集成测试

- 移动范围和 ZOC 对强行、飞将正确变化。
- 普攻、战法、计略、设施和城市命令通过现有公开入口触发特技。
- 乐奏只在所属势力开始行动前生效一次。
- 富豪、米道只影响基础收入，不影响事件收入和已有库存。
- 本地 intent 与联网 intent 在相同状态下产生完全相同的规范化 `GameState`。
- 旧存档、未知自定义特技和无特技武将继续正常读取。

### 15.3 最终验证

```powershell

npm.cmd run build
git diff --check
```

还需手动验证武将列表说明、出征主副将组合、移动范围、普通攻击、战法、计略、设施建设、本势力回合开始以及城市月度和季度收入。

## 16. 非目标

- 第一阶段不实现其余八十五种特技的实际效果。
- 不为尚不存在的俘虏、外交、婚姻、忠诚和异民族系统制造简化替代规则。
- 不改变当前战法、计略、设施和城市命令的基础数值，只有已激活特技明确修正结果。
- 不引入通用事件总线、反射式插件加载、运行时代码脚本或第三方规则引擎。
- 不修改联网协议、房间数据库结构或游戏存档版本。
